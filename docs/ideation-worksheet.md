# 송도 버스 도착 안내 및 자동 복구 서비스 — 아이디에이션 워크시트

송도 시민에게 지정 정류소의 버스 도착정보를 제공하고, 수집·LLM 출력·저장 장애를 제한적으로 복구합니다. 사용자가 확인한 정책을 반영했습니다. 정류소와 무료 API 등 연동 전 확인 사항은 미결정으로 유지합니다. 구현·검증을 완료했다는 뜻은 아닙니다.

# 1. 서비스 선정

## 1.1 대상과 정상 흐름

시민이 송도의 지정 정류소를 선택하면, 공공 버스정보를 수집하고 안내문을 생성한 뒤 형식·원본 일치를 검증하여 반환합니다. 운영자는 처리 상태와 복구 이력을 대시보드에서 확인합니다.

- 서비스명: 송도 버스 도착 안내 및 자동 복구 서비스
- 주요 사용자: 송도에서 버스를 이용하는 시민
- 운영 사용자: 프로젝트 팀
- 대상: 송도 정류소 1~3곳. 인천 연수구 송도로 해석했으며 정류소·방향·노선은 사용자 요청에 따라 [미결정]
- 표시 항목: 노선번호, 도착예정시간, 이전 버스 출발시각, 정보 갱신시각
- 이전 버스의 의미: 선택 정류소·방향에서 먼저 출발한 같은 노선의 앞선 차량
- 출발시각: 확인된 원천 데이터만 사용하며 미확보 시 “정보 없음”으로 표시

[인천광역시 도착정보 조회 API](https://www.data.go.kr/data/15059084/openapi.do)의 공개 명세에서 도착예정시간·노선 ID·버스 ID·최근 정류소를 확인했습니다. 해당 응답 표에 이전 버스 출발시각은 없습니다. 출발 이력 출처, 시민용 노선번호 매핑과 실제 정류소 제공 여부는 [미결정]입니다. 확인일은 2026-10-29이며 실제 인증 호출은 수행하지 않았습니다.

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 |
|---|---|---|---|
| 공공 버스 API | 정류소·노선·도착정보 조회 | 갱신 실패 | 가능 |
| 무료 LLM API 1종 | 안내 생성·장애 진단 두 역할 | 생성·진단 제한 | 가능, 실제 호출 검증과 구분 |
| Supabase | 결과·사건·복구 이력 저장 | 저장·이력 조회 실패 | 가능 |
| Redis | 최근 조회 결과·처리 상태 관리 | 캐시·처리 상태 조회 실패 | 가능 |
| 출발 이력 출처 [미결정] | 앞선 차량의 실제 출발시각 | 해당 항목 “정보 없음” | 실제 자료와 구분 |

## 1.2 중단 영향

시민은 도착정보를 보지 못하거나 오래된 정보로 이동을 판단할 수 있습니다. 운영자는 오류 확인과 재처리가 필요합니다. 데이터 누락·중복과 무료 API 한도 초과를 방지해야 합니다. 시민 개인 위치정보는 범위에 포함하지 않습니다. 서비스 선정 단계의 심각도는 중간이며 교통 운행·결제는 제어하지 않습니다.

## 1.3 수동 대응의 비교 기준

실제 운영 경험이나 소요시간 측정은 없습니다. 아래 내용은 사용자가 동의한 신규 서비스의 비교용 가정입니다.

| 단계 | 수동 대응 가정 | 확인 자료 | 소요시간 |
|---|---|---|---|
| 탐지 | 화면·오류 기록으로 실패 발견 | 응답·처리 상태 | 실측 없음 |
| 진단 | 오류와 원본·생성 결과 비교 | 오류 코드·검증 결과 | 실측 없음 |
| 복구 | 직접 재조회·재생성 | 실패 근거 | 실측 없음 |
| 검증 | 정상 응답·원본 일치 확인 | 재처리 결과 | 실측 없음 |
| 보고 | 결과·남은 문제 기록 | 사건 이력 | 실측 없음 |

자동화 대상은 제한된 재조회·재생성·저장 재시도입니다. 원인 불명, 인증·권한 문제, 한도 초과와 반복 실패는 운영자에게 전달합니다.

## 1.4 최소 범위와 환경

포함 범위는 정류소 1~3곳, 시민 화면, 운영 대시보드, LLM 두 역할, 독립 검증과 제한된 복구입니다. 출발 이력 미확보 시 “정보 없음” 표시는 정상적인 부분 정보 제공입니다.

전국 지원, 지도·경로 탐색·개인 알림, 자체 교통 예측, 근거 없는 출발시각 생성, 유료 API와 실제 교통 시스템 변경은 제외합니다.

팀은 부트캠프 3개월 경험의 4명이며 기간은 3일입니다. Python·Streamlit·LangChain·Supabase·Redis를 거의 필수로 활용하고 노트북에서 실행합니다. 프런트엔드·백엔드·에이전트 기능을 포함하지만 구체적인 백엔드 구성은 정하지 않았습니다. 운영체제, 자원, Redis 실행 방식과 Supabase 준비 상태는 [미결정]입니다.

LLM은 현재 웹 사용 계정만 있으며 무료 API를 준비할 의사가 확인됐습니다. 공급자·모델·무료 이용 조건과 실제 키 준비는 [미결정]입니다. 웹 계정 보유를 API 연동 가능 확인으로 간주하지 않습니다.

# 2. 에이전트 설계

## 2.1 장애 탐지

Monitor는 응답 오류·시간 초과·출력 검증 실패·저장 확인 실패를 관찰하고 사건과 근거를 생성합니다. 복구를 실행하지 않습니다. 별도 LLM을 사용하지 않습니다.

## 2.2 원인 진단

Diagnosis는 규칙으로 장애를 분류하고, LLM으로 근거를 해석·설명하는 역할을 담당합니다. 안내문 생성과 같은 무료 API 1종을 사용하되 목적·입력·출력을 구분합니다. 불명확한 진단이나 LLM 실패를 근거로 새 복구 행동을 만들지 않습니다.

## 2.3 복구 실행

Recovery는 허용된 재조회·안내문 재생성·중복 방지 저장 재시도만 수행합니다. 규칙 기반으로 실행하며 임의 명령, 인증정보 변경, 데이터 삭제·임의 수정, 유료 전환과 외부 서비스 재시작을 금지합니다.

## 2.4 독립 검증

Verification은 복구 실행과 독립된 규칙으로 정류소·방향·노선 일치, 필수 항목·형식, 원본과 안내의 일치, 수집 후 120초 이내 여부, 저장 결과·중복 여부를 검증합니다. 검증이 끝나기 전에는 복구 완료를 선언하지 않습니다.

## 2.5 오케스트레이터

Orchestrator는 규칙 기반으로 순서·사건 상태·시도 상한·전체 30초 제한·회로 차단·운영자 전달을 통제합니다. 별도 LLM을 사용하지 않으며 진단 결과가 정책을 우회하지 못하게 합니다.

## 2.6 협업 구조

| 역할 | 입력 | 출력 | 호출 주체 | 권한·실패 처리 |
|---|---|---|---|---|
| Monitor | 응답·시간·검증·저장 결과 | 사건·근거 | 관찰 흐름 | 읽기·기록만 수행 |
| 안내문 생성 LLM | 검증된 원본 | 구조화 안내 | 정상 흐름 또는 Recovery | 최초 포함 2회, 실패 시 기본 안내 검토 |
| Diagnosis LLM | 사건·최소 근거 | 장애 설명·허용 전략 후보 | Orchestrator | 임의 실행 금지, 판단 불가 시 운영자 전달 |
| Recovery | 허용 전략·남은 시도 | 수행 결과 | Orchestrator | 규칙에 따른 제한 실행 |
| Verification | 원본·수행 결과 | 통과·실패·근거 | 정상 흐름 및 Orchestrator | 읽기·검증, 미확인 성공 금지 |
| Notification | 사건·최종 상태 | 대시보드 알림·이력 | Orchestrator | 대시보드 기능으로 통합 |
| Orchestrator | 정책·역할 결과 | 다음 단계·최종 상태 | 처리 흐름 | 순서·기한·상한 통제 |

정상 생성 및 장애 흐름 모두 결과 게시 전 독립 검증을 거칩니다. 역할별 개별 제한은 전체 사건의 남은 시간 안에 설정합니다. 상세 값은 연동 준비 시 확인하되 PRD의 전체 시간 상한을 늘릴 수 없습니다.

# 3. 자율성과 통제

## 3.1 자동 실행 범위

공공 API 재조회, 오류 근거를 반영한 안내문 재생성, 중복 방지 저장 재시도와 원본 기반 기본 안내를 허용합니다. 검증된 원본이 없거나 수집 후 120초를 넘으면 도착정보 제공을 중단하고 상태를 알립니다. 기본 안내로 전환한 상태는 LLM 복구 성공과 구분합니다.

## 3.2 운영자 확인과 금지

API 키·공급자·복구 정책 변경과 수동 재개는 팀 담당자 확인이 필요합니다. 담당자 실명과 확인 대기시간은 [미결정]이며 미확인 상태에서는 관련 자동 변경을 수행하지 않습니다. 임의 명령·인증정보 자동 변경·데이터 삭제·유료 사용·외부 서비스 재시작은 금지합니다. 운영자 확인만으로 제외 범위를 확대하지 않습니다.

## 3.3 확정된 재시도 정책

| 항목 | 확정 기준 |
|---|---|
| 공공 API·저장 요청 | 최초 포함 최대 3회 |
| 공공 API·저장 요청의 재시도 대기 | 두 번째 시도 전 4초, 세 번째 시도 전 6초 |
| LLM 안내 생성 | 최초 포함 최대 2회 |
| 사건 자동 처리 | 최대 30초 |
| 최신성 | 수집 후 120초 이내 |
| 형식·원본 검증 | 규칙으로 수행, 부정확한 결과 게시 차단 |

4초·6초는 요청·저장 재시도 대기이며 LLM 재생성에 별도 대기를 추가하는 조건은 아닙니다. 30초에는 대기·호출·진단·검증이 포함됩니다. 남은 시간이 없으면 최대 횟수에 도달하기 전에도 중단합니다. 인증·권한·무료 한도 오류는 반복 재시도로 해결하지 않습니다. 시도 횟수 저장 방식은 [미결정]이며 상태를 신뢰할 수 없으면 자동 재시도를 중단해야 합니다.

## 3.4 무한 반복 방지와 재개

같은 의존 서비스에서 연속 3회 실패하면 60초간 차단합니다. 실패 횟수는 실제 시도의 실패를 기준으로 누적하며 성공이 독립 검증되면 초기화합니다. 안내 생성과 진단이 같은 LLM API를 쓰므로 호출 차단 상태를 공유합니다.

차단 중인 요청은 즉시 중단·안내하며 사건을 60초간 대기시키지 않습니다. 60초 후 확인 요청 1회만 허용하고, 성공 검증 시 재개합니다. 확인 실패 시 다시 60초간 차단합니다. 확인 요청도 새 처리의 30초 상한과 무료 호출 한도에 포함됩니다. 사건을 새로 만드는 방식으로 차단과 시도 제한을 우회하지 않습니다.

## 3.5 되돌리기·안전 중단

잘못된 안내문은 게시하지 않고 검증된 원본으로 기본 안내를 제공합니다. 저장 재시도에서는 같은 처리 결과를 중복 생성하지 않아야 합니다. 재조회 실패 시 기존 수집시각을 바꾸지 않으며 120초를 넘은 값은 최신 정보로 표시하지 않습니다. 한도·상한·검증 실패가 지속되면 자동 처리를 멈추고 근거와 상태를 운영자에게 전달합니다.

# 5. 검증

## 5.1 확정된 성공 기준

정상 조회와 장애별 모의 시나리오를 각각 3회 확인합니다. 잘못된 안내 게시 차단, 시도 상한 준수, 독립 검증 결과와 복구 성공 또는 안전 중단 기록이 모두 필수 통과 조건입니다. 최신성은 수집 후 120초 이내입니다. API의 원본 측정시각이 제공되면 수집시각과 구분하고, 수집 직후라는 이유로 원본 정보의 현재 정확성까지 보장하지 않습니다.

## 5.2 시간 측정

장애 주입·탐지·복구 시작·독립 검증 통과·안전 중단 시각을 사건 식별자에 연결합니다. 탐지 소요시간은 탐지−주입, 정상화 소요시간은 검증 통과−주입, 복구 실행 소요시간은 검증 통과−복구 시작입니다. 안전 중단에는 정상화 시각을 부여하지 않습니다. 시간 저장 방식은 [미결정]이며 사용자 표시는 한국 시간으로 제안합니다.

## 5.3 필수 로그

사건·추적 식별자, 대상·원본 기준시각·수집시각, 탐지·진단 근거, 선택 전략, 수행 결과, 시도·대기, 독립 검증, 승인·운영자 전달과 최종 상태를 기록합니다. 인증키와 불필요한 개인정보는 기록하지 않습니다. 저장 실패 중 대체 보존 방식·보존 기간·운영 접근 범위는 [미결정]이며 구현 전 확정합니다.

## 5.4 데모의 검증 계획

| 시나리오 | 안전한 재현 | 필수 증거 |
|---|---|---|
| 정상 조회 | 정상 모의 응답 | 대상·원본 일치·시각 |
| API 오류 | 모의 오류 응답 | 실패·대기·시도·검증 |
| 지연 | 모의 지연 | 기한 준수·결과 또는 중단 |
| 형식 오류 | 잘못된 모의 출력 | 검증 실패·재생성·게시 차단 |
| 내용 불일치 | 원본과 다른 모의 출력 | 원본 대조·게시 차단 |
| 저장 실패 | 모의 저장 오류 | 중복 없는 재시도·확인 또는 중단 |
| 반복 실패 | 오류 지속 | 연속 실패·차단·확인 요청·운영자 전달 |
| 이력 미확보 | 출발 이력 없음 | “정보 없음”, 출발시각 생성 없음 |
| 오래된 자료 | 수집 후 120초 초과 | 정상 실시간 표시 차단 |

정상 조회와 다섯 필수 장애는 각각 3회 확인합니다. 반복 실패·이력 미확보·오래된 자료의 경계 조건도 별도 검증 대상으로 기록합니다. 실제 LLM 호출 결과와 모의 결과는 구분합니다. 위 항목은 향후 인수 검증 요구사항이며 오늘 테스트 파일 작성이나 실행을 하지 않습니다.

# 6. 3일 범위

Day 1은 서비스 선정·워크시트 검토·PRD 작성·승인까지입니다. Day 2의 작업분해·구현·검증과 Day 3의 통합·장애 재현·측정·데모는 오늘 실행하지 않습니다. 원본 양식에 있는 Day 1 작업목록 승인은 오늘 범위에서 제외합니다.

# 7. 최종 범위와 남은 결정

필수 제공 범위는 지정 정류소 안내, 두 LLM 역할, 독립 검증, 제한된 복구와 운영 대시보드입니다. 지역·기술·무료 사용 조건과 제외 범위는 1절을 따릅니다.

| ID | 남은 사항 | 조건·결정 시점 |
|---|---|---|
| D-01 | 정류소·방향·노선 | 사용자 요청으로 미결정 유지, 데이터 연동 전 선정 |
| D-02 | 무료 LLM 공급자·모델·키·한도 | 연동 전 실제 사용 조건 확인, 유료 자동 전환 금지 |
| D-03 | 출발 이력·노선번호 매핑 출처 | 미확보 출발 이력은 “정보 없음”, 기본 도착정보의 제공 가능성은 연동 전 확인 |
| D-04 | 실행 환경·저장·접근·로그 상세 | 구현 전 구체화, 정해진 시간·횟수·안전 조건 유지 |
| D-05 | 팀명·작성자·검토자·운영 담당자 | 최종 승인·운영 준비 시 기록 |

새로운 필수 출처나 무료 API를 확보하지 못하면 실연동 완료로 표시할 수 없습니다. 무료 조건에서 실제 두 LLM 역할을 구현할 수 없으면 범위 재검토가 필요하며 모의 결과로 실제 동작을 대체했다고 주장하지 않습니다.

# 8. 검토 승인

- 서비스 범위: 확정
- 핵심 정책: 사용자 답변 반영 완료
- 반영 내용: 정류소 미결정 유지, LLM 두 역할·공급자 한 종류, 요청·저장 재시도 대기 4초·6초, 수동 대응의 가정 표시, 검증 목표 승인
- 문서 상태: PRD 초안 작성의 입력으로 사용, 최종 PRD 승인 대기
- 실제 구현·실험·검증: 미수행
