# 송도 버스 도착 안내 및 자동 복구 서비스 PRD

## 1. 문서 정보

| 항목 | 내용 |
|---|---|
| 버전 | 0.1 |
| 작성일 | 2026-10-29 |
| 상태 | 초안 — 사용자 최종 승인 대기 |
| 독자 | 4인 개발팀과 요구사항 검토자 |
| 작성자·팀명·검토자 실명 | [미결정] |
| 근거 | 승인된 서비스 선정 결과, 아이디에이션 워크시트 0.2, 사용자의 정책 확인 답변 |

이 문서는 시민용 버스 안내와 장애 자동 복구의 제공 범위·권한·인수조건을 정의합니다. 서비스 선정과 핵심 정책은 사용자 확인을 받았으며 세부 요구사항은 이 초안의 최종 검토 대상입니다. 구현·장애 주입·검증은 수행하지 않았습니다. 오늘은 이 문서의 검토와 승인까지만 진행합니다.

## 2. 프로젝트 개요

시민이 송도의 지정 정류소를 선택하면 공공 버스정보를 수집하고, LLM이 생성한 안내를 독립 검증하여 제공합니다. 수집·출력·저장 장애에는 사전에 허용한 복구만 제한적으로 수행합니다. 운영자는 대시보드에서 원인과 시도·검증·최종 상태를 확인합니다.

| 조건 | 범위 |
|---|---|
| 대상 | 송도 정류소 1~3곳, 정류소·방향·노선은 [미결정] |
| 팀·기간 | 부트캠프 3개월 경험의 4명, 3일 프로젝트 |
| 실행 환경 | 노트북, 구체적인 자원·운영체제는 [미결정] |
| 기술 | Python·Streamlit·LangChain·Supabase·Redis를 활용하는 조건 |
| LLM | 안내문 생성·장애 진단 두 역할, 같은 무료 API 한 종류 사용 |
| 비용 | 무료 API 이용 범위, 유료 자동 전환 금지 |

실제 무료 API 사용 자격·키·모델과 대상 데이터 제공 여부는 아직 확인되지 않았습니다. 이 문서 승인과 실제 연동 준비 완료를 구분합니다.

## 3. 문제 정의

시민은 정류소에서 버스 도착예정정보를 확인해야 합니다. 수집 API가 실패하거나 늦게 응답하면 최신 안내를 제공하기 어렵고, LLM이 정해진 형식을 어기거나 원본과 다른 시간을 생성하면 부정확한 안내가 표시될 수 있습니다. 저장 실패는 운영자가 처리 경과를 확인하기 어렵게 만듭니다.

운영자가 오류를 확인하고 직접 재조회·재생성·결과 확인을 하는 상황을 수동 대응의 비교 기준으로 둡니다. 이는 사용자가 동의한 신규 서비스의 가정이며 실제 장애 경험이나 실측 시간이 아닙니다. 수동 대비 개선율과 시간 절감 실적은 주장하지 않습니다.

자동화의 목적은 실패 신호를 일관되게 기록하고, 제한된 복구 뒤 결과를 독립 판정하며, 해결되지 않는 장애를 운영자가 판단할 수 있도록 전달하는 것입니다.

## 4. 사용자와 이해관계자

| 대상 | 필요한 결과 | 권한·범위 |
|---|---|---|
| 송도에서 버스를 이용하는 시민 | 선택 정류소·방향의 노선번호·도착예정시간·이전 출발시각·갱신시각 | 지정 대상 조회, 시스템 복구 정책 변경 불가 |
| 프로젝트 운영자 | 수집·검증·복구 상태, 실패 근거와 이력 | 사건 확인, 합의된 수동 대응·재개 판단 |
| 개발팀·검토자 | 명확한 범위·역할·검증 기준 | 구현 전 미결정 사항 확인, 최종 요구사항 검토 |

운영 담당자 실명과 운영 화면 접근 통제 방법은 [미결정]입니다. 시민에게 복구 제어와 비밀키를 노출하지 않아야 합니다. 시민의 개인 위치정보·계정 정보는 MVP 수집 범위에 포함하지 않습니다.

## 5. 목표와 성공 기준

| 목표 | 인수 기준 | 확인 방법 |
|---|---|---|
| 정상 안내 | 지정 정류소·방향·노선과 원본에 일치하는 안내 제공 | 정상 모의 시나리오 3회 모두 통과 |
| 형식·내용 검증 | 잘못된 형식·수치·노선의 안내를 시민에게 게시하지 않음 | 형식 오류·내용 불일치 시나리오 각각 3회 모두 차단 |
| 제한된 복구 | 공공 API·저장 최초 포함 최대 3회, LLM 안내 생성 최초 포함 최대 2회 | 사건별 호출·대기 기록 확인 |
| 처리기한 | 사건 자동 처리 30초 이내에 복구 검증 완료 또는 안전 중단 | 시작·검증·중단 시각 비교 |
| 최신성 | 수집 후 120초를 초과한 결과를 정상 도착정보로 게시하지 않음 | 경계 조건의 표시 상태 확인 |
| 추적 가능성 | 탐지·진단·시도·검증·최종 상태가 연결됨 | 각 필수 시나리오의 사건 기록 확인 |
| 반복 실패 통제 | 의존 서비스 연속 3회 실패 시 60초간 차단, 이후 확인 요청 1회 | 연속 오류·차단·재개 경계 확인 |

다섯 필수 장애는 8절에 정의합니다. 일시 장애의 회복 결과와 지속 장애의 안전 중단을 모두 검증합니다. 안전 중단이나 기본 안내 전환을 자동 복구 성공으로 집계하지 않습니다. 위 수치는 프로젝트 목표이며 실제 외부 버스 정보의 정확성 또는 운영 서비스 가용성을 보장하는 실적이 아닙니다.

## 6. 비목표

전국 정류소 지원, 지도·경로 탐색·개인 맞춤 알림, 자체 도착시간 예측, LLM의 근거 없는 출발시각 생성, 유료 API 사용, 실제 교통 시스템 변경을 제외합니다. 임의 명령 실행, 자동 인증정보 변경, 데이터 삭제·임의 수정과 외부 서비스 재시작을 복구 기능으로 제공하지 않습니다.

오늘은 코드·테스트·배포 파일, 개발 작업목록, 설치·실행·실제 장애 주입·Git 커밋을 수행하지 않습니다. 후속 단계의 구현 계획을 개발 태스크로 분해하지 않습니다.

## 7. 정상 서비스 시나리오

1. 시민이 미리 지정된 송도 정류소와 방향을 선택합니다.
2. 서비스가 해당 대상의 버스 도착정보를 수집합니다. 유효한 캐시를 사용할 경우 원래 수집시각을 유지합니다.
3. 수집 결과의 대상·필수 정보·유효성을 확인합니다.
4. 안내문 생성 LLM에 검증된 원본만 전달하여 구조화 안내와 짧은 설명을 생성합니다.
5. 별도 규칙 검증이 형식, 원본 일치와 수집 후 120초 이내 여부를 확인합니다.
6. 시민 화면에 노선번호, 도착예정시간, 확인 가능한 이전 버스 출발시각, 정보 갱신시각을 표시합니다.
7. 운영 대시보드에 수집·생성·검증·저장 상태를 표시합니다.

도착예정시간은 예측 정보로 표시합니다. 재표시·캐시 조회·LLM 재생성만으로 원래 수집시각을 갱신하지 않습니다. 수집 시점 기준 상대시간을 표시 시점에 변환할 경우 경과시간을 반영하되 이를 새로운 원천 데이터로 취급하지 않습니다.

이전 버스 출발시각은 같은 정류소·방향·노선에서 앞서 출발한 차량의 확인된 실제 출발시각입니다. 이력 출처가 없으면 “정보 없음”을 표시합니다. 차량의 조회 목록 제외, 남은 시간 0, 예상 도착시각으로 실제 출발을 추정하지 않습니다.

현재 [인천광역시 도착정보 조회 API](https://www.data.go.kr/data/15059084/openapi.do)의 공개 명세에서 도착예정시간·노선 ID·차량 ID·최근 정류소가 확인되며 이전 버스 출발시각 항목은 확인되지 않았습니다. 노선 ID를 시민용 노선번호에 연결할 자료와 대상 정류소의 제공 여부는 구현 전 확인해야 합니다. 확인일은 2026-10-29이며 실제 API 호출 검증은 하지 않았습니다.

## 8. 장애 시나리오

모든 장애는 향후 격리된 모의 의존 서비스를 통해 재현합니다. 실제 공공기관이나 외부 서비스에 장애를 유발하지 않습니다.

| ID | 장애·발생 위치 | 탐지 가능한 신호 | 시민·운영 영향 | 안전한 재현 |
|---|---|---|---|---|
| F-01 | 수집 API 일시 오류 | 오류 응답·업무 오류 코드 | 정보 갱신 실패 | 모의 오류 응답 |
| F-02 | 수집 API 응답 지연 | 요청 시간 초과 | 조회 지연·처리 중단 | 모의 응답 지연 |
| F-03 | LLM 출력 형식 오류 | 파싱 실패·필수 항목 누락·타입 불일치 | 안내문 표시 제한 | 잘못된 모의 출력 |
| F-04 | LLM 내용 불일치 | 노선·시간 등이 원본과 다름 | 잘못된 이동 판단 위험 | 원본과 다른 모의 출력 |
| F-05 | Supabase 저장 실패 | 오류·저장 확인 실패 | 이력 누락·중복 위험 | 모의 저장 오류 |

운행 중인 차량이 없다는 정상 응답, 출발 이력 미제공과 실제 수집 장애를 구분합니다. 정상적으로 비어 있는 결과만으로 복구를 시작하지 않습니다.

인증·권한 오류, 무료 이용 한도 초과와 원인 불명은 무조건 재시도하지 않고 운영자에게 전달합니다. Redis 장애로 상태의 신뢰성이 사라지면 캐시 정상 판정과 자동 재시도를 중단하고 제한 상태로 전환합니다. Redis 전용 추가 장애 시나리오는 필수 다섯 장애와 구분합니다.

## 9. 멀티 에이전트 구성

두 LLM 역할은 같은 무료 API를 사용하되 목적과 입력·출력을 분리합니다. 장애를 요약하는 설명 능력과 시민 안내를 생성하는 능력을 구분하고, 복구 권한은 규칙 기반 실행에만 둡니다. 아래 역할 구분은 별도 프로세스나 서버 수를 정하는 요구가 아닙니다.

### 안내문 생성 LLM

- 책임: 검증된 버스정보를 시민용 구조화 안내로 변환합니다.
- 입력: 선택 대상, 원본 도착정보, 확인된 출발 이력 또는 미제공 상태, 시각 정보입니다.
- 출력: 필수 정보를 가진 안내와 짧은 설명입니다.
- 사용할 수 있는 정보: 해당 조회의 검증된 원본만 사용합니다.
- 허용 행동: 원본을 요약하고 검증 실패 근거에 따라 재생성합니다.
- 금지 행동: 시각·노선 추정, 비밀키 접근, 데이터 저장·복구 실행입니다.
- 실패 시 행동: 총 2회와 전체 기한 안에서 재생성하고 이후 기본 안내 또는 제한 상태로 전환합니다.

### Monitor

- 책임: 처리 실패 신호를 탐지하고 사건을 만듭니다.
- 입력: 응답 상태·시간, 형식·내용 검증 결과, 저장 결과입니다.
- 출력: 대상·유형·탐지시각·근거를 연결한 사건입니다.
- 사용할 수 있는 정보: 필요한 응답·처리 상태와 검증 기록입니다.
- 허용 행동: 읽기·관찰·사건 기록입니다.
- 금지 행동: 설정 변경과 복구 실행입니다.
- 실패 시 행동: 관찰 불가 상태도 기록하고 운영자에게 전달합니다.

### Diagnosis LLM

- 책임: 규칙 분류를 바탕으로 장애 근거를 해석하고 허용 전략을 설명합니다.
- 입력: 사건과 비밀정보를 제거한 최소 증거, 허용 전략 목록입니다.
- 출력: 분류·근거·허용 전략 후보 또는 판단 불가입니다.
- 사용할 수 있는 정보: 사건에 연결된 원본·오류·시도 근거만 사용합니다.
- 허용 행동: 근거 해석과 설명입니다.
- 금지 행동: 임의 명령 생성·실행, 정책 우회와 복구 직접 실행입니다.
- 실패 시 행동: 규칙으로 확정 가능한 분류만 사용하고 그 외에는 원인 불명으로 전달합니다. 진단 LLM 호출은 사건당 1회를 상한으로 두며, 호출 불가·실패 시 무한 재진단하지 않습니다. 이 호출도 전체 30초와 공유 무료 한도에 포함됩니다.

### Recovery

- 책임: 허용된 복구 전략만 수행합니다.
- 입력: 정책으로 확인한 전략, 남은 횟수·시간과 차단 상태입니다.
- 출력: 수행 결과·실패 근거·시도 기록입니다.
- 사용할 수 있는 정보: 해당 사건과 제한 상태, 필요한 대상 정보입니다.
- 허용 행동: 재조회·안내 재생성 요청·중복 방지 저장 재시도입니다.
- 금지 행동: 데이터 삭제, 인증정보 변경, 외부 서비스 재시작, 유료 전환과 임의 명령입니다.
- 실패 시 행동: 상한·기한·차단 조건에 따라 중단하고 검증 결과와 함께 전달합니다.

### Verification

- 책임: 정상·복구 결과를 독립 규칙으로 검증합니다.
- 입력: 원본, 게시 후보, 저장 결과, 대상과 수집시각입니다.
- 출력: 항목별 통과·실패와 근거입니다.
- 사용할 수 있는 정보: 해당 처리의 원본과 결과를 읽습니다.
- 허용 행동: 대상·형식·원본 일치·최신성·저장 여부 검증입니다.
- 금지 행동: 원본 수정, 복구 실행, 검증 없는 성공 선언입니다.
- 실패 시 행동: 미확인 결과를 차단하고 재시도 또는 안전 중단 판단에 전달합니다.

### Orchestrator

- 책임: 순서·상태·기한·시도·차단·운영자 전달을 규칙으로 통제합니다.
- 입력: 사건, 정책과 각 역할의 결과입니다.
- 출력: 다음 단계와 최종 상태입니다.
- 사용할 수 있는 정보: 관련 사건·카운터·차단·검증 기록입니다.
- 허용 행동: 허용된 역할 호출과 상태 전이입니다.
- 금지 행동: 권한·시도·기한 우회와 LLM 제안의 직접 실행입니다.
- 실패 시 행동: 상태가 불명확하면 자동 변경을 멈추고 운영자에게 전달합니다.

### Notification

- 책임: 운영자가 볼 사건·확인 필요 사항·최종 상태를 대시보드에 제공합니다.
- 입력: 사건, 진단·시도·검증 결과와 전달 사유입니다.
- 출력: 운영 화면 알림과 처리 이력입니다.
- 사용할 수 있는 정보: 비밀정보를 제거한 사건 기록입니다.
- 허용 행동: 대시보드 표시·확인 상태 기록입니다.
- 금지 행동: 복구 정책 변경과 임의 외부 메시지 발송입니다.
- 실패 시 행동: 알림·기록 실패를 숨기지 않고 대체 확인 수단의 조건을 남깁니다.

Monitor·Recovery·Verification·Orchestrator는 규칙 기반으로 구성하고 Notification은 대시보드에 통합합니다. 실제 무료 모델이 두 LLM 역할을 수행할 수 있는지는 연동 준비 시 확인합니다.

## 10. 에이전트 협업 흐름

정상 흐름은 수집 → 원본 검증 → 안내 생성 → 독립 검증 → 시민 표시입니다. 실패가 발견되면 Monitor가 사건을 만들고 Orchestrator가 규칙 분류와 Diagnosis의 설명을 받아 허용 복구를 선택합니다.

Orchestrator는 호출 전 횟수·남은 시간·의존 서비스 차단·무료 한도를 확인하고 Recovery를 호출합니다. Verification이 결과를 확인한 뒤에만 정상화를 선언합니다. 결과가 실패하면 제한 안에서 반복하거나 중단합니다. Notification은 운영 대시보드에 근거와 최종 결과를 표시합니다.

형식 오류 후 내용 오류가 발생해도 안내 생성 총 2회는 동일한 처리에서 공유합니다. 신규 사건 생성이나 역할 분리로 상한을 초기화하지 않습니다. 같은 LLM API를 쓰는 두 역할은 해당 의존 서비스의 차단·호출 한도를 공유합니다.

최종 결과는 정상 처리, 독립 검증된 자동 복구 성공, 기본 안내로 기능 축소, 안전 중단·운영자 전달로 구분합니다. 저장 실패가 남아 있는 상태를 완전 복구로 표시하지 않습니다.

## 11. 장애별 복구정책

| 장애 | 탐지 신호·진단 근거 | 1차 복구 | 2차 대응 | 최대 시도 | 사람 확인 | 되돌리기·안전 중단 | 성공 검증 |
|---|---|---|---|---|---|---|---|
| F-01 API 오류 | 오류 응답·코드 | 4초 후 재조회 | 실패 시 6초 후 재조회 | 최초 포함 3회 | 상한·지속 실패 시 | 게시 제한·운영자 전달 | 유효 원본·대상·최신성 |
| F-02 지연 | 응답 시간 초과 | 4초 후 재조회 | 실패 시 6초 후 재조회 | 최초 포함 3회 | 상한·지속 실패 시 | 30초 기한에서 중단 | 유효 응답과 기한 준수 |
| F-03 형식 오류 | 필수 항목·형식 검사 실패 | 오류 항목으로 재생성 | 기본 안내 또는 중단 | 최초 포함 2회 | 반복 실패 시 | 잘못된 후보 미게시 | 형식과 원본 대조 모두 통과 |
| F-04 내용 불일치 | 원본과 결과 불일치 | 후보 차단 후 재생성 | 기본 안내 또는 중단 | 최초 포함 2회 | 반복 실패 시 | 잘못된 후보 미게시 | 형식과 원본 대조 모두 통과 |
| F-05 저장 실패 | 오류·저장 확인 실패 | 4초 후 중복 방지 재시도 | 실패 시 6초 후 재시도 | 최초 포함 3회 | 상한·지속 실패 시 | 추가 저장 중단 | 저장 확인·중복 없음 |

요청·저장의 4초·6초는 첫 실패 후 두 번째 시도, 두 번째 실패 후 세 번째 시도 앞의 대기입니다. LLM 안내 생성에 이 대기를 자동 적용하지 않습니다. 새 호출은 남은 처리시간 안에 완료·검증할 수 있는 범위에서만 시작합니다.

사건 자동 처리는 첫 실패 탐지부터 최종 결과까지 최대 30초로 제한하며, 대기·진단·복구 호출·검증을 모두 포함합니다. 최초 정상 요청의 응답 제한과 사건 탐지 후의 전체 제한은 구분합니다. 시간 초과로 중단된 호출의 늦은 결과가 이후 게시되거나 성공으로 처리되지 않아야 합니다. 개별 호출 제한은 무료 모델·API 응답 특성을 확인해 정하되 전체 30초를 늘릴 수 없습니다.

의존 서비스별 실제 시도가 연속 3회 실패하면 60초간 차단합니다. 성공이 독립 검증되면 실패 누적을 초기화합니다. 차단 중 요청은 대기시키지 않고 제한 상태를 반환합니다. 60초 후 확인 요청 1회만 허용하며 성공 검증 시 재개하고 실패하면 다시 60초간 차단합니다. 확인 요청도 무료 한도와 새 처리의 기한을 따릅니다.

기본 안내는 유효 원본을 직접 표시하는 규칙 기반 결과입니다. LLM 실패가 해소됐다는 의미가 아니므로 LLM 복구 성공으로 기록하지 않습니다. 유효 원본도 없으면 도착정보를 임의로 채우지 않고 조회 실패를 표시합니다.

## 12. 자율성과 Human-in-the-loop

| 범주 | 행동 | 조건 |
|---|---|---|
| 자동 실행 가능 | 지정 대상 재조회·안내 재생성·중복 방지 저장 재시도·기본 안내 | 시도·시간·무료 한도·검증 정책 준수 |
| 사람 확인 후 실행 | 키·공급자·복구 정책 변경, 합의된 수동 재개 | 담당자 확인과 변경 이유 기록 |
| 자동 실행 금지 | 임의 명령, 인증정보 변경, 데이터 삭제·임의 수정, 외부 서비스 재시작, 유료 사용·확장 | MVP 범위 밖 |

원인 불명, 인증·권한·한도 오류, 상한·전체 기한 도달과 상태 불신뢰 시 운영자에게 사건·근거·시도·검증·권고를 전달합니다. 대시보드 전달은 제품 요구사항이며 오늘 실제 외부 메시지를 발송하지 않습니다.

확인 담당자·확인 대기시간은 [미결정]입니다. 미확인 상태에서는 관련 자동 변경을 하지 않습니다. 사람의 확인을 받더라도 제외 범위를 자동 확대하지 않습니다.

## 13. 기능 요구사항

### FR-001 지정 정류소 조회

- 설명: 미리 정한 1~3곳에서 정류소·방향을 선택합니다.
- 입력: 지정 대상 중 하나입니다.
- 기대 동작: 일치하는 노선·도착정보만 처리합니다.
- 예외 상황: 미지정 대상, 방향 불명확, 정상 빈 응답입니다.
- 인수조건: 다른 정류소·방향 자료를 섞지 않고 빈 응답을 수집 장애와 구분합니다.

### FR-002 공공 데이터 수집과 검증

- 설명: 도착정보의 대상·필수 항목·상태를 확인합니다.
- 입력: 공공 API 응답과 수집시각입니다.
- 기대 동작: 유효 원본만 다음 단계로 전달합니다.
- 예외 상황: 업무 오류, 지연, 인증·한도 오류와 누락입니다.
- 인수조건: F-01·F-02를 탐지하고 인증·한도 오류를 무조건 재시도하지 않습니다.

### FR-003 이전 버스 출발시각

- 설명: 같은 정류소·방향·노선에서 앞선 차량의 확인된 출발시각만 표시합니다.
- 입력: 출처가 확인된 출발 이력 또는 미제공 상태입니다.
- 기대 동작: 실제 확인값 또는 “정보 없음”을 반환합니다.
- 예외 상황: 출처 없음, 차량 구분 불가, 다른 방향 이력입니다.
- 인수조건: 미제공을 장애로 오인하지 않고 시각을 추정·생성하지 않습니다.

### FR-004 LLM 안내문 생성

- 설명: 무료 API를 사용하는 생성 역할이 원본을 안내로 변환합니다.
- 입력: 검증된 원본과 미제공 상태입니다.
- 기대 동작: 노선번호·도착정보·출발 이력 상태·갱신시각을 포함한 구조화 안내를 만듭니다.
- 예외 상황: 오류·한도·잘못된 출력입니다.
- 인수조건: 최초 포함 2회 이내이며 출력 규격을 구현 전 합의하고 두 LLM 역할의 입출력을 구분합니다.

### FR-005 출력 형식·내용 독립 검증

- 설명: LLM과 별도 규칙이 게시 후보를 검사합니다.
- 입력: 원본과 생성 결과입니다.
- 기대 동작: 형식 및 원본 대조를 모두 통과해야 게시합니다.
- 예외 상황: 한 검사만 통과하거나 검증 자체가 실패합니다.
- 인수조건: F-03·F-04에서 잘못된 후보가 한 번도 시민에게 게시되지 않습니다.

### FR-006 최신성·시민 표시

- 설명: 데이터의 시간과 상태를 시민이 구분하게 합니다.
- 입력: 결과·원래 수집시각·표시시각·원본 기준시각입니다.
- 기대 동작: 수집 후 120초 이내의 유효 자료만 정상 도착정보로 표시합니다.
- 예외 상황: 캐시 오래됨, 원본 기준시각 미제공, 조회 실패입니다.
- 인수조건: 120초 초과 자료의 정상 표시를 차단하며 캐시 조회·재생성으로 수집시각을 변경하지 않습니다.

### FR-007 사건 탐지·진단

- 설명: 실패와 최소 근거를 연결하고 진단 LLM이 해석합니다.
- 입력: 오류·시간·검증 실패와 허용 전략 목록입니다.
- 기대 동작: 장애 유형·근거·허용 전략 후보 또는 판단 불가를 반환합니다.
- 예외 상황: 진단 실패·차단·한도 초과입니다.
- 인수조건: 확실한 규칙 분류만으로 제한 복구하거나 원인 불명으로 전달하며 새로운 임의 행동을 실행하지 않습니다.

### FR-008 제한된 복구·흐름 제어

- 설명: 허용된 전략의 시도·대기·시간을 관리합니다.
- 입력: 사건·정책·카운터·남은 시간입니다.
- 기대 동작: 4초·6초 대기와 호출 상한을 준수합니다.
- 예외 상황: 남은 시간이 부족하거나 상태를 신뢰할 수 없습니다.
- 인수조건: 전체 30초 또는 더 이른 상한에서 중단하며 사건 재생성으로 제한을 우회하지 않습니다.

### FR-009 반복 실패 차단·재개

- 설명: 같은 대상의 실패 반복을 억제합니다.
- 입력: 의존 서비스별 연속 실패·차단 상태입니다.
- 기대 동작: 3회 실패 시 60초 차단 후 확인 요청 1회를 허용합니다.
- 예외 상황: 동시 확인 요청·확인 실패입니다.
- 인수조건: 같은 LLM API의 두 역할이 차단을 공유하고 확인 요청이 중복되지 않습니다.

### FR-010 결과 저장과 중복 방지

- 설명: 결과와 사건 이력을 Supabase에 저장합니다.
- 입력: 처리 결과·식별자·검증 상태입니다.
- 기대 동작: 저장 결과를 확인하고 같은 처리의 중복을 방지합니다.
- 예외 상황: 저장 실패·성공 여부 불명확입니다.
- 인수조건: F-05에서 최초 포함 3회와 대기 정책을 지키며 저장 미확인 상태를 성공으로 표시하지 않습니다.

### FR-011 캐시·처리 상태 관리

- 설명: Redis의 결과와 상태를 사용하되 원래 시각·제한을 유지합니다.
- 입력: 대상별 결과·수집시각·처리 상태입니다.
- 기대 동작: 유효 자료만 재사용하며 재시도와 차단 상태를 일관되게 관리합니다.
- 예외 상황: 상태 읽기 실패·일부 유실·오래된 값입니다.
- 인수조건: 상태 불명확 시 상한을 초기화해 자동 재시도하지 않고 제한 상태와 운영자 전달로 전환합니다.

### FR-012 기본 안내·운영 대시보드

- 설명: 생성 실패 시 기본 안내를 제공하고 운영자는 처리 경과를 확인합니다.
- 입력: 유효 원본, 사건·진단·시도·검증·저장 결과입니다.
- 기대 동작: 유효 원본이 있으면 기본 안내, 없으면 조회 제한을 표시하고 운영 상태를 분리합니다.
- 예외 상황: 기록 저장·알림 실패입니다.
- 인수조건: 정상·복구 성공·기본 안내·안전 중단을 구분하고 실패 이유와 남은 문제를 숨기지 않습니다.

이 절은 개념 정보 요구사항이며 상세 저장 스키마나 파일 구조를 확정하지 않습니다.

| 원본 출처·기준시각·수집시각·응답 상태 | 원본 대조와 최신성 판단 |
| 출발 이력 값·출처·미제공 상태 | 확인된 시각과 미제공 구분 |

Supabase는 결과·이력 보관, Redis는 최근 조회·처리 상태 관리에 사용합니다. 저장 실패 중에도 대체 보존할 최소 근거와 복원·조회 방식은 구현 전에 결정해야 합니다. 기록을 확인할 수 없으면 관측 가능성 인수조건은 미충족으로 표시합니다.

시각은 같은 기준으로 비교하며 한국 시간 표시는 권고안입니다. 저장 형식·동기화·보존 기간·상태 유실 대응과 운영 접근 방법은 [미결정]입니다. 시민 화면은 필요한 안내만 제공하고 운영 기록·비밀키를 노출하지 않습니다.

## 16. 검증 및 완료 기준

검증은 향후 단계에서 수행하며 오늘 테스트 파일·명령 작성이나 실행은 하지 않습니다.

| 시나리오 | 확인 횟수 | 필수 통과 기준 |
|---|---|---|
| 정상 조회 | 3회 | 대상·원본·형식·최신성·화면 결과 일치 |
| F-01 API 일시 오류 | 3회 | 4초·6초 대기, 총 3회 이내, 검증 또는 중단 |
| F-02 응답 지연 | 3회 | 전체 30초 상한, 늦은 결과 게시 방지 |
| F-03 형식 오류 | 3회 | 총 2회 이내, 형식과 원본 검증, 잘못된 출력 게시 차단 |
| F-04 내용 불일치 | 3회 | 원본 대조 실패 탐지, 잘못된 출력 게시 차단 |
| F-05 저장 실패 | 3회 | 중복 방지·저장 확인, 총 3회 또는 더 이른 기한에서 중단 |

다음 경계 조건도 별도 확인합니다. 확인 횟수의 추가 수치는 정하지 않으며 정책을 충족하는 근거가 있어야 합니다.

- 일시 오류가 회복된 경우와 오류가 계속되는 경우의 결과 구분
- 형식·내용 오류가 번갈아 발생해도 같은 생성 상한 공유
- 연속 3회 실패, 60초 차단, 확인 요청 성공·실패와 재차단
- 수집 후 120초 이내와 초과 시 표시 차이, 캐시 조회 시 시각 불변
- 출발 이력 미확보 시 “정보 없음”과 근거 없는 시각 생성 없음
- 정상 빈 응답과 장애의 구분
- 인증·한도·원인 불명 오류의 안전 중단
- Redis 상태 불신뢰 시 제한 우회 방지와 저장 실패 중 근거 보존
- 잘못된 복구 결과 미게시, 기본 안내 후 기능 정상 여부

복구 성공률은 자동 복구가 필요한 사건 중 독립 검증을 통과한 사건의 비율로 표시하고 분모·건수를 함께 기록합니다. 기본 안내·안전 중단·운영자 전달은 별도로 집계합니다. 탐지 소요시간은 탐지−주입, 정상화 소요시간은 독립 검증 통과−주입입니다. 실패 사건에는 정상화 시각을 만들지 않습니다. 평균값은 성공·실패 대상을 명확히 구분하며 측정하지 않은 수치를 채우지 않습니다.

필수 통과 조건이 모두 확인되고, 남은 연동·환경 결정이 해결되며, 실제 두 LLM 역할의 호출을 확인해야 구현 완료로 판단할 수 있습니다. 모의 결과만으로 실제 연동·LLM 동작 완료를 선언하지 않습니다.
